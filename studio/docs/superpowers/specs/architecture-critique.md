# 独立架构审查结论：REVISE

当前规格方向基本符合用户目标，但尚未达到可实施状态。主要阻塞点是：后端承载方案未决、双向投影只定义了方向未形成完整接口契约、完整虾塘的真实操作与现有目标实现之间存在明显能力缺口。

## 七维评级

| 维度 | 评级 | 判断 |
|---|---|---|
| 1. 需求与质量属性一致性 | 🟡 | 产品边界和“不纳入模块”写得清楚，但“完整虾塘”与当前仅有目录/部分写回桥接之间仍有落差。 |
| 2. 边界质量 | 🔴 | DramaClaw 后端、Go 适配层、Next.js 页面、CanvasProject 之间的所有权和接口边界尚未确定。 |
| 3. 模式克制 | 🟢 | 明确拒绝通用 `assets` CRUD 和泛化 `/jobs`，整体没有明显的架构过度设计。 |
| 4. 数据与状态建模 | 🔴 | 投影元数据有方向性描述，但项目身份、实体 ID、媒体槽位、revision、写回状态和一致性约束尚未形成可执行契约。 |
| 5. 变更容忍度 | 🟡 | 已命名未来模块并避免暗中纳入，但“逐项完整移植”仍缺少最小稳定适配面。 |
| 6. 失败与规模现实性 | 🟡 | 识别了部分失败、重复写入和 stale read 风险，但未定义跨服务部分失败后的恢复协议。 |
| 7. 决策记录与可读性 | 🟡 | 方案 A/B 和待确认事项明确，但关键决策被留给实施前，导致当前规格不能作为稳定实施输入。 |

## 具体发现

### blocker 1：后端承载未决，完整功能没有唯一系统边界

- **维度**：边界质量、数据建模
- **规格锚点**：第 4.2 节方案 A/B；第 11 节第 1 项待确认。
- **代码事实**：当前目标路由主要暴露目录和部分写回接口：`router/router.go:100-119`；目标页面实际调用 `fetchDramaImportCatalog`，并通过本地 store 投影：`web/src/features/xiaji/xiaji-client-page.tsx:94-112`、`154-215`。
- **问题**：方案 A 要求同部署 DramaClaw 服务和 Go 逐项代理，方案 B 则要求迁移持久化、路径和领域规则。两者的认证、项目 ID、文件路径、任务状态和错误语义都不同。未选定方案时，页面和 API 无法确定谁拥有角色、场景、道具、声线的真实状态。
- **最小修订方向**：在进入实施计划前锁定 A 或 B；同时给出一张边界表，明确每类数据的系统记录、读写方、认证主体、媒体存储方和任务状态来源。

### blocker 2：用户要求的“虾画内添加虾塘内容”尚未在现有实现中形成闭环

- **维度**：需求一致性、边界质量
- **规格锚点**：第 2 节成功标准第 4 项；第 5 节第 3 项；第 6.1 节跨页投影。
- **代码事实**：当前 `XiaJiClientPage` 实现了虾塘页面向画布发送，并在发送后跳转画布：`web/src/features/xiaji/xiaji-client-page.tsx:154-215`。代码中没有显示画布内选择器或当前画布导入入口。路由现有 DramaClaw API 也只有目录、上传、identity、push、impact、角色 history/restore：`router/router.go:100-119`。
- **问题**：规格允许工具栏或右键菜单“至少一种”，但没有确定入口、调用路径、选择器复用方式或当前画布上下文传递方式。双向投影因此仍是产品意图，而不是接口设计。
- **最小修订方向**：明确首期入口；定义 `list/select/project` 的请求和响应契约；规定当前 `CanvasProject` 如何传入、投影失败时是否部分提交，以及页面发送和画布内添加如何共用同一个投影函数。

### blocker 3：完整虾塘操作清单没有映射到可实施接口

- **维度**：需求一致性、数据建模
- **规格锚点**：第 2 节成功标准第 2 项；第 6.1 节角色、场景、道具、声线操作清单。
- **代码事实**：源端确有大量领域路由，例如场景 CRUD、全景、导演世界和生成：`integrations/dramaclaw/src/novelvideo/api/routes/scenes.py:880-1434`；道具 CRUD/生成：`props.py:193-394`；项目旁白声线操作：`projects.py:764-905`；任务查询和流式状态：`tasks.py:327-606`。
- **问题**：规格只列出能力名称，没有逐项绑定到目标 API、请求字段、返回结构、异步任务类型、权限检查和写回语义。比如“3GS 生成与结果读取”依赖何种 task type、结果文件如何关联场景、失败后怎样恢复，都没有确定。
- **最小修订方向**：为四类页签各列出“源端端点 → 目标端点 → 数据模型 → 状态接口 → 错误/恢复语义”的映射表；未完成映射的操作不得进入“完整可用”承诺。

### should-fix 4：项目上下文仍依赖手工输入 ID，与独立虾集页面目标不一致

- **维度**：需求一致性、边界质量
- **规格锚点**：第 5 节第 1 项；第 11 节第 1、2 项。
- **代码事实**：当前页面要求用户输入 DramaClaw 项目 ID：`web/src/features/xiaji/xiaji-client-page.tsx:135-145`、`249-255`。
- **问题**：规格要求按项目上下文工作且“不要求主要流程反复复制粘贴项目 ID”，但当前设计没有定义项目列表、当前项目绑定、创建项目或身份映射机制。此处也直接受“虾料是否纳入”影响。
- **最小修订方向**：明确项目上下文来源：目标项目选择器、DramaClaw 项目列表、固定映射，或用户首次绑定后持久化。若暂时只能手输 ID，应把它标记为临时能力，不宣称完整独立工作台。

### should-fix 5：投影去重和 revision 规则没有覆盖并发与跨标签页写入

- **维度**：数据建模、失败与规模现实性
- **规格锚点**：第 5 节第 5 项；第 6.1/6.3 节。
- **代码事实**：当前投影直接读取客户端 store、合并节点并更新项目：`web/src/features/xiaji/xiaji-client-page.tsx:193-205`。规格明确不承诺跨标签页、跨设备 exactly-once，但没有定义冲突处理。
- **问题**：两个标签页同时导入或保存时，稳定来源键只能抑制单次客户端流程中的重复，不能防止后写覆盖先写。`revision` 也没有规定是目录 revision、实体 revision 还是媒体文件版本。
- **最小修订方向**：明确首期并发边界；至少规定保存冲突检测、revision 不匹配时的用户动作，以及投影重复时“跳过/新增副本/更新节点”的选择。

### should-fix 6：部分媒体失败后的投影语义可能丢失用户选择

- **维度**：失败与规模现实性
- **规格锚点**：第 5 节第 6 项；第 6.3 节。
- **代码事实**：当前代码在媒体拉取失败后仍继续创建投影，并提示“未能拉取，已从画布投影中略过”：`web/src/features/xiaji/xiaji-client-page.tsx:188-190`、`208-211`。
- **问题**：这满足“错误可见”，但没有定义缺失媒体是否仍创建带错误状态的占位节点、用户是否能稍后补拉、重复发送时如何识别已部分完成的投影。用户要求的是可追溯投影，单纯略过会使源资产和画布内容不对称。
- **最小修订方向**：为每个媒体投影定义 `pending/ready/failed` 状态；失败项保留来源元数据和重试动作，避免整次投影只能以“成功但缺少内容”结束。

### should-fix 7：写回接口的幂等与不确定结果处理仍停留在原则层面

- **维度**：数据建模、失败与规模现实性
- **规格锚点**：第 6.2、6.3 节。
- **代码事实**：规格承认 `/freezone/push` 没有幂等保证，并要求避免盲重试；但没有定义请求状态查询、操作 ID 或人工核对接口。
- **问题**：网络超时后，客户端无法判断替换是否已经发生，只能停止重试或让用户重新操作。对“候选上传 → identity 创建 → 槽位替换”这种多阶段流程，缺少可恢复的中间状态。
- **最小修订方向**：为每次写回建立客户端可追踪的操作记录；至少定义上传结果、源端确认、目标槽位状态和未知结果四种状态，以及查询/继续/放弃动作。

### nit 8：许可证核验被留到实施前，不能作为当前复用承诺的已解决条件

- **维度**：决策记录与可读性
- **规格锚点**：第 9 节。
- **代码事实**：移植页面文件带有 `SPDX-License-Identifier: Elastic-2.0`：`web/src/features/xiaji/xiaji-client-page.tsx:3-5`；规格同时声明目标仓库为 AGPL-3.0。
- **问题**：规格正确地提醒了许可证风险，但没有确定哪些源文件会被复制、哪些只作为行为参考，也没有确认发布组合条件。
- **最小修订方向**：在实施前形成文件级来源清单和许可证处理决策；在此之前将“直接移植源码”表述为待许可证核验的方案，而非已确定的复用方式。

## 缺失的关键决策、接口与恢复问题

1. **后端承载决策**：A 或 B 必须先定。
2. **项目上下文接口**：当前用户、DramaClaw 项目、目标虾集页面和 CanvasProject 如何绑定。
3. **四类实体契约**：角色身份、场景资源槽位、道具参考图、角色/旁白声线的稳定 ID 和媒体角色。
4. **任务契约**：哪些操作同步，哪些异步；任务类型、状态读取、结果关联和失败重试。
5. **双向投影契约**：画布内入口、当前画布提交方式、投影节点类型、部分失败和重复导入策略。
6. **写回恢复协议**：超时、不确定结果、候选已上传但正式写入失败时如何查询和继续。
7. **并发模型**：多标签页、跨设备、源端修改后再投影、画布保存冲突如何处理。
8. **完整范围判定**：如果某项角色/场景/声线操作暂时没有端点，页面是否隐藏、禁用，还是必须先补齐后再交付。
9. **许可证边界**：源文件复制与重新实现分别采用什么方式。

## 最小修订建议

1. 先锁定后端承载方案，并补充系统边界表。
2. 把第 6.1 节改成逐操作接口矩阵，覆盖请求、响应、任务状态、权限和恢复。
3. 明确虾画内添加入口，并定义与“发送到虾画”共用的投影契约。
4. 定义项目上下文绑定，消除主要流程中的手工项目 ID 依赖。
5. 为投影和写回补充状态机：成功、部分成功、失败、未知结果、可恢复。
6. 明确首期并发和 revision 规则。
7. 在实施前完成文件级许可证核验。
8. 将“完整虾塘”验收标准改为可逐项勾选的操作清单；未完成映射的操作不得标记为真实可用。

本审查为建议性意见；按 `architecture-critic` 的判定规则，因存在红色维度和 blocker，当前 verdict 为 **REVISE**。
