## 首轮记录中的 chunk 404 恢复方案（已由最新状态更新）

### 已核实事实

- 浏览器访问 `http://localhost:3000` 时，动态页 HTML 可返回 200，但客户端所需的两个 Next chunk URL 返回 404，页面抛出 `ChunkLoadError`。
- 3000 listener 的命令行观察为 `node ... next start --hostname 127.0.0.1 --port 3000`；运行进程的工作目录、仓库 root 与 Next build root 未确认。
- 本机启动器 `launch-infinite-canvas.ps1` 在检查或替换现有 3000 前可能先触发前端 build；其 `Test-CanvasReady` 只验证页面 HTML 与 API bridge。故恢复计划不得盲目运行该一键启动器，也不能把它报告 ready 当成 chunk 已加载。
- 当前 checkout `.next/static/chunks` 存在相同文件名；没有证据证明它就是正在运行的进程加载并向 HTTP 提供的构建。
- 配置 `web/next.config.ts` 设为 `output: "standalone"`，生产运行脚本用 `next start`；本地开发文档说明该方式用于规避 Windows standalone/pnpm 链接的 `EPERM`。这是需要对照运行日志及真实文件树核对的配置差异，不足以单独断定根因或修复方式。
- 曾在 3101 观察到独立 origin 被重定向至登录页；因此 3101 不能作为无条件的 3000 会话/数据等价验收环境。

### 当前推断与未确认项

服务运行时引用的 manifest 与静态文件不一致是一个解释，但并未确认。其他可能性包括进程指向另一工作区、实际服务静态目录与当前 checkout 不同、构建产物缺文件或另一类客户端错误。必须在实际进程/构建目录内比对 BUILD_ID、manifests、HTML 引用和 HTTP 状态后才能下结论。

### 采用的恢复门

此段是首轮 404 后拟定的恢复门。最新续跑已在 3000 完成项目内虾塘和虾镜 E2E，因此不再阻塞当前验收。历史故障根因仍未知；如果复现，再按只读取证确认进程、目录、manifest 与 chunk，然后决定是否需要单独的 build/停服变更单。

这是首轮恢复分析记录；之后已进行最新续跑并另行更新本文顶部、规格、计划及架构。该分析本身没有执行构建、服务操作或浏览器测试。
